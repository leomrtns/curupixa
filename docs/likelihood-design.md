# Likelihood backend direction
Likelihood evaluation remains a future implementation, as requested. The current tree, alignment and workspace APIs establish the ownership and data boundaries needed by that work. This document records a design direction, rather than an installed likelihood ABI.
## Data ownership
Keep the topology in `crpx_tree`: three connectivity indices per node, optional labels and optional branch lengths. Keep an immutable alignment and its pattern weights separate. Each concurrent analysis owns its model parameters and mutable numerical workspace. Conditional likelihood vectors, transition matrices, scaling buffers, rate categories and site-repeat tables belong to that workspace, with arrays indexed through a node-to-backend mapping. Neither the alignment nor the backbone needs a likelihood pointer.
An analysis can share a read-only tree and alignment across workers. Each worker owns its conditional vectors, traversal operations and random stream. MPI ranks own their process-local state; the application decides how to partition sites, trees or proposals and how to reduce scores. Curupixa must not initialise MPI, change thread counts or perform hidden collectives.
## Preparing an evaluation
1. Validate taxon labels and build an explicit mapping from alignment taxa to tree leaves. Node IDs do not imply taxon order or backend buffer order.
2. Choose the state alphabet, ambiguity mapping, substitution model, rate categories, scaling convention and root treatment. The current alignment helpers provide four-state DNA masks and tip vectors; other alphabets need explicit maps.
3. Convert a refreshed postorder traversal into backend operations. Handle polytomies through a documented operation expansion or return a recoverable unsupported status. Preserve branch lengths and taxon identity during any expansion.
4. Allocate numerical buffers with the backend's required alignment and padded state size. Convert pattern weights and indices with range checks when the backend uses narrower integer types.
5. Initialise tip information and model state, update transition matrices and evaluate partials. Return an owned result or caller-provided outputs with status information; copy any backend diagnostic while it is valid.
6. Verify the implementation against an independent small-tree reference, then compare model/partition log likelihoods with the selected engine. Include ambiguity, zero-length branches, saturation, large trees, rate mixtures and scaling stress cases.
## Invalidation and proposals
The current tree revision conservatively invalidates every derived workspace after a tree mutation, including label or length changes. A future likelihood workspace should also track independent generations for alignment patterns, model parameters and category rates. Only introduce finer topology/length generations when a measured use case justifies their additional API.
Make proposal state explicit: retain accepted numerical buffers or record the affected operation/buffer indices so rejection can restore them. A single `updated` flag cannot describe independent upward/downward partials for several concurrent analyses. The current optional update flags are worker-owned and serve as a starting point for separate likelihood validity arrays.
## Candidate adapter
The upstream [libpll-2 repository](https://github.com/xflouris/libpll-2) describes site-repeat support and identifies itself as the official fork of libpll. Its [public header](https://github.com/xflouris/libpll-2/blob/master/src/pll.h) separates partitions, operation lists, conditional vectors, transition matrices and scaler indices. These provide a useful adapter boundary. Curupixa can translate its own traversal and node IDs directly to numerical operations; adopting the backend's pointer-based tree representation is unnecessary for the core API.
Select and pin an upstream version before implementing that adapter. Check its actual error-state, allocation, SIMD, state-order and threading contracts at that version, and keep dependency discovery optional. The upstream repository identifies its licence as AGPL-3.0; record the chosen backend and its licence explicitly when adding it. No backend has been linked or vendored by this update.
